## Anomalies BLOQUANTES

Toutes reproduites par le rédacteur avec des scripts distincts de ceux du sondeur.

### HAT3-A1 — `fold` ignoré dans la comparaison d'instants de même `tzinfo`

Python compare en heure murale deux `datetime` partageant le même `tzinfo`, sans tenir compte de
`fold`. Le code compare les instants sans les ramener en UTC.

```python
NY = ZoneInfo("America/New_York")
DatasetSnapshot(**{**kw, "as_of": datetime(2020, 11, 1, 1, 30, tzinfo=NY),            # 05:30Z
                         "availability_cutoff": datetime(2020, 11, 1, 1, 20, fold=1, tzinfo=NY)})  # 06:20Z
# accepté ; l'aller-retour JSON du même objet est rejeté (ValidationError)
```

- **C02-INV-01** violé à la construction (cutoff postérieur à `as_of`). La même faille s'applique à
  `time_range_start`/`time_range_end`.
- **QCT-1** (« ordre des lignes croissant … instant chronologique ; clés dupliquées interdites ») :
  une clé primaire `datetime` en `America/New_York` sort 06:15Z avant 05:45Z ; la même table exprimée
  en UTC produit d'autres octets, donc une autre empreinte (**INV-06/INV-07**). Deux instants
  distincts (05:45Z et 06:45Z) sont rejetés comme clé dupliquée.
- Facette calendrier (`regular_close_local` avec `fold=1`) rapportée par le sondeur, même cause
  racine, non retenue séparément.

### HAT3-A2 — `tzinfo` mutable aliasé dans un objet validé

**C02-INV-05** (« tout objet atteignable … non modifiable »). Un `tzinfo` dont `utcoffset()` lit un
état mutable (modèle `LocalTimezone` de la documentation Python) est conservé par référence.

```python
s = DatasetSnapshot(**{**kw, "availability_cutoff": datetime(2020, 7, 15, 12, 0, tzinfo=tz)})
tz.offset = timedelta(hours=-5)
s.availability_cutoff > s.as_of   # True : INV-01 violé après validation ; model_dump_json() change
```

### HAT3-A3 — `Knowable` à valeur mutable

**C02-INV-05**, type commun `Knowable`. `Knowable.known(["a"]).value.append("X")` modifie l'état.
Portée limitée aux `Knowable` autonomes (les champs `Knowable` des modèles C02 ont des types
immuables), mais `Knowable` est un type public C02 couvert par l'invariant.

### HAT3-A4 — `verify_artifacts` sensible à l'ordre avec plusieurs artefacts invalides

**C02-INV-09** (« le résultat de la vérification, succès ou message, est invariant par
permutation ») et P-03. Avec deux artefacts invalides (dicts ou objets forgés), la revalidation
lève la première erreur dans l'ordre fourni : deux permutations produisent deux messages distincts
(`content_sha256` / `byte_size`). Le `ProfileReport` diffère également selon la permutation.

### HAT3-A5 — CRED-1 V2 : correspondances non chevauchantes

`CRED-1.grammar` (« détectée quelle que soit sa position »). Un mot de schéma consomme le suivant
comme jeton, et la recherche reprend après lui :

| Valeur | Résultat |
|--------|----------|
| `token abc123def456` | V2 |
| `basic token abc123def456` | `None` |
| `Bearer Bearer eyJhbGciOiJIUzI1NiJ9` | `None` |

Cas absent de `CRED-1.limits`.

### HAT3-A6 — CRED-1 V4 : `@` dans le nom d'utilisateur

V4 (« scheme://[utilisateur]:[motdepasse]@ ») ; seule limite déclarée : userinfo sans `:`.
`ftp://john@corp.example:hunter2@ftp.host/` et `https://user@corp:S3CRET@host/x` ne sont pas
détectés (`urlsplit(...).password == 'hunter2'`).

### HAT3-A7 — V1 à V4 non appliqués aux clés

`CRED-1.scope` (« clés et valeurs ») et **C02-INV-18** (« aucun indicateur … dans les champs du
périmètre »). Les clés `https://u:S3CRET@host`, `Basic dXNlcjpwYXNzd29yZA==` et `?key=abc123` sont
acceptées. Le contrat ne réserve nulle part V1–V4 aux valeurs ; seule la docstring du code le fait.
CA-03 doit soit appliquer V1–V4 aux clés, soit restreindre explicitement le texte normatif.
